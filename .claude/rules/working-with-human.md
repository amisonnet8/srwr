# 人間とのやり取り

**人間は、ほぼ「OK」を押すだけで進められ、重要な場面だけはきちんと確認できる**ようにする。そのために、人間に頼むときの形を決めておく。原則は3つ。

1. **小さなつまずき**は、原因と「してほしいこと」を短く頼む。人間は「やる／やらない」だけを判断する
2. **人間がする確認**は、準備から比較まで自動にする。人間は見て OK／NG を付けるだけ。1コマンドで、何度でも同じ手順
3. **UI に関わる段階の始め**は、箇条書きのポイント資料とデザインのサンプル画像を作り、了承をもらってから実装する

## 1. 頼む前に、どの種類かを決める

| 種類 | 例 | どうするか |
|---|---|---|
| **小さなつまずき**（原因が分かっている） | サンドボックスで書けない・つなげない、ツールが入っていない、`sudo` が要る、`.claude/settings.json` の変更が要る | 2章の形で頼む。**質問にしない** |
| **些細な判断** | 名前、置き場所、どちらでもよい実装の選び方、文書の言い回し、テストの分け方 | **聞かない。** 決めて進み、`mtqg m add` に「決めたこと・理由」を残す。迷ったら後で変えやすい方を選ぶ |
| **重要な判断** | UI の見た目・振る舞い、テープやプロトコルの形式、依存の追加、取り消せない操作、`docs/` の方針と食い違うこと | 必ず聞く。**推奨案を先頭にした選択肢**で聞く（`AskUserQuestion`）。各案の影響を1行ずつ。`mtqg q add` に残す |

**してはいけないこと**
- 「〜できませんでした。どうしますか」と、原因も案も無しに渡す
- 原因を人間に調べさせる（エラーを読む、設定を見る、のは AI の仕事）
- 選択肢だけを並べて、推奨を出さない
- 長い手順を人間に読ませる、手で打たせる

## 2. 小さなつまずきの頼み方（原則1）

**先に、自分で原因を調べる。** エラー文、`.claude/settings.json`、`.claude/rules/testing.md` の「Bashサンドボックスの落とし穴」を見る。原因が分からないうちは頼まない。どうしても分からないときは、試したことを1行で書き、人間に動かしてほしい**確認のコマンド1つ**を出す。

頼むときは、この形で、**5行以内**にする。

```
【お願い】<何が止まったか>
原因：<1行>
してほしいこと：<コピペで動くコマンド1つ、または設定の差分>
やらない場合：<代わりにどう進めるか>
```

例1：サンドボックスの書き込み先

```
【お願い】qsoku lint がキャッシュを書けずに止まりました
原因：~/.cache/golangci-lint がまだ無く、サンドボックスが作れません
してほしいこと：ターミナルで mkdir -p ~/.cache/golangci-lint
やらない場合：lint は飛ばし、vet とテストだけで先に進みます
```

例2：接続先の許可（`.claude/settings.json` は人間が管理するので、差分で示す）

```
【お願い】Vim 9.0.0784 のビルドで github.com 以外への接続が拒否されました
原因：codeload.github.com が許可リストに無い
してほしいこと：.claude/settings.json の network.allowedDomains に "codeload.github.com" を1行足す
やらない場合：古い Vim での確認は CI に任せ、手元では最新の Vim だけで確かめます
```

決まり
- コマンドは**コピペでそのまま動く1つ**（`&&` でつないでよい）。`<ここを書き換える>` のような穴を残さない
- 設定ファイルの変更は、**どのキーに何を足すか**を具体的に書く（人間は貼るだけ）
- 頼むことが複数あるときは、**まとめて1回**で頼む
- 返事を待つ間も、止まらずにできることを進める（「やらない場合」の道で進めてよい）
- 頼んだこと・結果は `mtqg m add` に残す。同じつまずきを2回したら、`.claude/rules/testing.md` の落とし穴に足す

## 3. 人間がする確認（原則2）

詳しい方針と作り方は `handoff/checklist/CHECKLIST.md`（1〜4章）。要点：

| 原則 | 内容 |
|---|---|
| 人間がやるのは「見て判断する」だけ | 準備（ビルド、作業場、テープ）、起動、操作（コマ送り、ライブの流し込み）、画面の取得、基準との比較は、**すべて自動** |
| 1コマンドで始まる | 人間に渡すのは `qsoku ui-check`・`qsoku ui-open …` のようなコマンド1つと、できあがったページ（`ui-check-result/latest/index.html`）だけ。ページは見るだけで、OK／NG は人間がチャットで答え、AI が `qsoku ui-accept`（NG は `qsoku ui-accept ng <ひとこと>`）で記録する。OK で、違う画面・新しい画面が次の基準になる（基準の変更はコミットする） |
| 何度でも同じ結果 | 毎回、作業場を作り直す。固定テープは書き換えない。`sleep` ではなく条件を待つ |
| 機械で確かめられることは頼まない | 色の値・文言・行番号・画面の数・スクロール位置・新着の数などは、テストで確かめる |
| 変わったところだけ見てもらう | 基準（前回 OK）と今を並べ、**差があるものだけ**を見てもらう |
| 結果を残す | OK／NG・日時・対象の版をファイルに保存し、次の基準にする |
| 「ない」ものを確認させない | 固定テープに無い場面を確認項目にしない。要るなら、本物の `srwr mcp` でテープを作るところまで自動にする |

- **確認を頼む前に、その確認の自動化を作る。** まだ無いなら、それはその段階の作業に含める（`dev/roadmap.md`）。手順を文章で渡して代わりにしない
- 頼むときは、この形にする（`handoff/checklist/CHECKLIST.md` 4-4）

```
【確認のお願い】<変えたこと>
1. qsoku ui-check            （または qsoku ui-open vscode why-basic など、1つ）
2. 開くページ：<パス>。自動の検証が全部通っていること
3. 手順と見るところ（項目ごと）：<番号つきの操作の手順。どこを押し、何を待ち、どのコマの何を見るか>
4. 判断するのは：<CHECKLIST 4-2 の番号> だけ
```

- **人間は、チャットや質問欄の文字をコピーできないことがある。** 打たせるコマンドは短い `qsoku …` の1行にし、長いコマンドやパスを打たせない。Vim で打たせるキー・コマンドも最小にする（`:set background=light` のような入力は、`-light` の付いた名前にして打たせない）。キーを打たせる手順には、**日本語入力（IME）を切る**ことを書く（IME が入っていると、`]]` や `:` が Vim に届かず、「打った文字が出ない」と見える。R5 で起きた）
- **確認してほしい項目は、1つ残らず、操作の手順まで書く。** 「ライブで追えるか見てください」のように見るところだけを渡さない。どのコマンドを打ち、どこを押し、何を待ち、いつ何を見るか（時間に限りがある操作は、その時間も）を、項目ごとに番号つきで書く。人間に手順を聞き返させない（R4 で、ライブの確認の手順を聞かれた）
- 人間の答えは `AskUserQuestion` の「OK／直す」で受け、`mtqg q add` に残す

## 4. UI に関わる段階の始め（原則3）

**対象**：`dev/roadmap.md` で【UIゲート】の印がある段階。ほかの段階でも、VSCode・Vim の画面、`srwr view` の一覧や案内、利用者が目にする CLI の出力の見え方に関わる作業を始めるときは、同じようにする。

**実装を始める前に**、`dev/review/<段階>/` に次の3つを作る。

| ファイル | 中身 |
|---|---|
| `README.md` | **箇条書きのポイント**。1画面に収まる長さ。①この段階で作るもの、②どの画面がどう見えるか、③従う確定デザイン（画像の名前）、④新しく決めること（あれば。推奨案つき）、⑤了承してほしいこと |
| `images/` | 見てほしい画像（dark と light）。**確定済みの画面は `handoff/design/images/` から写す。** 新しい画面・変える画面だけ、案を SVG で描く（描き方は `handoff/design/DESIGN.md` 12章：Vim は 140桁×50行の端末、VSCode は VSCode 風） |
| `index.html` | `README.md` の要点と画像を、1枚に並べたページ（外部の読み込みなし。ブラウザで開くだけで見える） |

- **`index.html` は、本物の HTML で書き、画像（SVG）を埋め込んだ1ファイルにする。** 画像を相対パスで参照すると、開く環境によって出ない。`README.md` の Markdown を `<pre>` に流し込まない（R4 で2回やり直した）
- 人間には、2章の形の短い依頼で `dev/review/<段階>/index.html` を開いてもらい、`AskUserQuestion` で「了承／直す」を選んでもらう
- **了承されてから実装する。** 了承の内容は `mtqg q add`（質問と回答）に残す。「直す」なら直して出し直す
- 確定済みのデザイン（`handoff/README.md`）は、ゲートでも変えない。変えるのは新しい画面だけ。決まった新しい画面は、`handoff/design/DESIGN.md`・`images/`・`handoff/ui/UI.md` と、`docs/reference/vscode.md`・`vim.md` に足す
- ゲートで見せたものと違う見た目を作らない。作ってみて変える必要が出たら、もう一度ゲートを通す
