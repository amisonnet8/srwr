# 設計上の判断と理由

*[English](decisions.md) | **日本語***

**読者**：srwr の作りを知りたい人、開発に加わる人。「なぜそうなっているか」を知りたいとき。決まりそのものは [reference の文書](../reference/cli_ja.md)、範囲トークンの理由は [token.md](token_ja.md)。

## 編集の仕組み

### Edit / Write は、指示ではなく設定で禁止する

最大のリスクは、「AI が必ず2コマンド経由で編集するか」を、指示文書だけで守らせることだった。Claude Code なら、プロジェクトの `.claude/settings.json` で組み込みの編集ツールを禁止できる。

```json
{ "permissions": { "deny": ["Edit", "Write", "MultiEdit", "NotebookEdit"] } }
```

これでファイルを変える正規の手段は srwr だけになる。確かめたいことも、「ルールを守るか」から「**2コマンドだけで仕事ができるか**」に変わる。Bash 経由の編集（`sed -i`、リダイレクトなど）は塞げないので、`external` で検知して見せる。これが厳格モード（[cli.md](../reference/cli_ja.md)）。利用者が好むなら、禁止せず hook で記録する緩いモードも選べる。

### `look` と `edit`：見ることが、変えることの前にある

中身を返すだけの `look` は、AI から見ると「手間だけで得るものがない」呼び出しになり、省略されやすい。最初の設計では、`select` しないと `replace` できず、`select` は省略できない手順だった。実際には、AI は別のツール（`sub`、場所ごとの2回の呼び出し）で省略した：ある実験では、`sub` の74回のうち69回が1か所だけの変更で、`select` → `replace` は2回しか使われなかった。そこで、ツールを作り直した：`look`（見る。返すトークンを `edit` が受け取れる）、`edit`（範囲を直す。1回の呼び出し）、`replace`（同じ変更を複数の場所に。1か所には使えなくする）、`new`。変更のたびに範囲がテープに残るので、テープには今も「見る → 変える」が残る。

### `edit` は、トークンなしでも `file` と `expect` で範囲を指せる

同じ実験で、トークンが edit を送りにくくしていることが分かった。edit のたびに先に `look` が要り、呼び出しを並列にできず、同じファイルの複数箇所は下から順に直す必要があった。そこで `edit` は `file` と `expect`（範囲が持っている行）も受ける。`expect` は必須（挿入を除く）：行番号が言うからというだけの場所へ書き込んではいけないので、`look` の `expect` と同じ確かめにした。範囲は、渡された行番号、最後の look 以降の変更でずらした行番号、`expect` のただ1か所、の順で決める。前の2つは AI が見たものに沿う方法で、最後は、それが成り立たないときの網。前の2つが別の場所を指すときは、推測せず `content_ambiguous` にする。挿入は確かめる行がないので、look のあとファイルが変わっていないときだけ受け付ける。「look して、トークンで edit」の流れは、説明にも例にも、最初の edit の方法として残す。

### `replace` は2か所以上のため。1か所は `edit` で行う

ある実験では、旧 `sub` の呼び出し 74 件のうち 69 件が1か所だけの変更だった。いちばん短い方法で、テープに範囲が残らず、「見て、変える」が記録されなかった。そこで `replace` は、文字列が1か所だけにあるのに `count` が 1 のとき、断る（`use_edit`）。答えに、その場所と、同じ変更をする `edit` の呼び出しを付けるので、`edit` に替える手間は呼び出し1回で、考えなくてよい。見るのは `count` で、ツールの決まりではないので、複数の場所があるのに `count` が 1 なら、ふつうの `count_mismatch`。結果は、最初の場所から最後の場所までの全行でなく、場所ごとに1件（今の行と、前後1行）で、トークンは返さない。AI は続きを `look` で行っていたし、長い結果は毎回の手間になる。

### 空白（スペース・タブ）の違いは、行つきで知らせる（`nearMatches`）

AI は、ファイルがタブなのに `expect`・`old` をスペースで書く（またはその逆）ことが多く、「見つからない」とだけ言われて、理由を知るためにファイルを読み直していた。そこで、空白の連続と行末の空白を除けば見つかるとき、その場所を、今の行のまま `nearMatches` で知らせる。次の呼び出しで、そのまま写せる。`actual` はコードごとに形が違うので、その中でなく隣に置く。入れるのはファイルの行だけで、**テープには書かない**（テープに載る `message` は場所しか言わない）。畳むのは空白だけで、違う単語は「近い」とはしない（間違った手がかりは、手がかりがないより AI の手間になる）。`expect` が行の一部だけのとき（再実験2で3回起きた）も同じ：空白だけ違う場所がなければ、`expect` を行の一部として含む行を `nearMatches` に入れ、`message` で「`expect` は行全体で書く」と伝える。

### `look` で検索でき、当たりはどれも look になる

実験で、AI はファイルを `look` でなく Read や `sed`・`grep` で読んだ。テープには `why` のない hook の記録しか残らず、編集の前には、結局もう一度 `look` を呼んでいた。`search`（ただの文字列、1ファイル、1行の中）つきの `look` は、当たった行をトークンつきで返すので、探すことと編集することが srwr の中の1本の道になる。返した当たりは、同じ `why` で、その行の `look` としてテープに書く。トークンは、元の `look`（`seq`）を要るし、再生で AI が何を見たかも分かるため。テープの形式も画面も変わらない。正規表現と複数ファイルは入れない：パターンの書き間違いという失敗が増え、広い場合は `replace` と hook が受け持つため。

### `edit` は `edits` で、1つの理由の複数の編集を、全部行うか何も行わないかで受ける

AI は、似た編集を5〜10か所、同じ `why` で1つずつ送り、そのたびにビルドの hook が走った。`edit` の `edits` なら、1回で行える。5つ目のツールではなく `edit` の一部で、テープは変えない：項目ごとに `edit` が1つ、各ファイルの上から順に、1つずつ送ったのと同じに書く。範囲は全部、呼ぶ前のファイルで決めるので、項目同士は関係せず、順番は自由（行番号は AI が見たもの）。重なる範囲は、どの順でも正しくならないので断る。ファイルを先に書いてからテープ、は今までどおり（間で落ちたら、次の呼び出しが `external` として見つける）。1つの項目の誤りは何も変えず、エラーがどの項目かを言う。

### `before`・`after` でなく `above`・`below`

`edit` の結果（と `replace` の `hits`）にある、新しい範囲のすぐ上とすぐ下の行（今のファイルの行）は、`before`・`after` と呼んでいた。AI はこれを「変更の前と後の内容」と読み、置き換える前の行を求めた。場所を言う `above`・`below` に改め、説明にも「置き換える前の内容ではない」と書いた。テープは変えない（テープの `before`・`after` は全文のことで、別のもの）。

### `insert`：残す行の隣に新しい行を足す

AI は「ある行の後ろに1行足したい」と思った。空の範囲でもできるが、最後の look のあとファイルが変わっていない間だけで、AI は隣の行を `expect` と `newText` に書き直し、書き間違えることがあった。`insert: "after"`（または `"before"`）なら、行はいつもと同じに指す（トークン、または `file` と `expect`。`expect` は確かめる）ので、ファイルが変わったあとでも場所を確かめられる。その行は残り、`newText` がその隣に入る。新しいツールでもテープのイベントでもなく、呼び出しの項目の1つ。テープには、今までどおり空の範囲の `edit` が入る。

### `old` と `new` は、`expect` とは別に、行の一部を直す

### v0.1.9 で AI に伝えることを増やした理由と、増やしすぎない理由

3つの実験で小さなつまずきが見つかり、どれも新しい入力か1行の案内で答え、推測はしない。`brief` は既定でなく入力にした：返ってくる行は、ファイルを読み直さずに編集を確かめる手段で、確かめなくてよいときを AI が選ぶ。`insert: "start"|"end"` は、場所がファイルの先頭か末尾で動かないから、look も `expect` も要らない。挿入で2つのかたまりがくっついたときは、`hint` で知らせるだけで、空行は足さない：かたまりが何か（関数、段落、表）は言語で違い、外れるとファイルを変えてしまう。`look` は読むだけなので範囲外の `endLine` を切るが、`edit` は切らない：書く範囲は、意図した場所そのものでなければならない。`old` のときの片方の行番号は探す場所のヒントで、`old` が1か所だけという条件は同じなので、安全は下がらない。ディレクトリの `search` は、git と同じにファイルを数え（無視されるものは読む価値がない）、記録しないものは何も言わずに飛ばし、テープには当たりのあったファイルだけを書く（作業場を探しただけで、誰も見ていないファイルがテープに溢れないように）。Bash がファイルを作った・変えたときの hook の案内は穏やかにする：ジェネレーターや整形ツールが書くのはそのままでよく、手で書くときに理由を残す道を伝えるだけ。

実験で、AI が長い行（表の行）を丸ごと `expect` に写して数語だけ直そうとし、1〜2文字の違いで6回失敗した。`expect` は行全体のままにする。`file` と `expect` の安全は、AI が見た行のあるところにだけ書くことだから。行の一部は別の入力にした：`old` と `new`（ファイルの中にただ1か所ある文字列と、その代わり）。安全は別の確かめ方で同じにする：`old` は、渡した行の中（あれば）、なければファイルの中で1か所だけでなければならず、違う場所は推測せずに断る。新しいツールではなく `edit` の入力で、テープには `expect` のときと同じ、行全体の `edit` が入る（`old`・`new` そのものは書かない）。`replace` の `use_edit` も同じ `old`・`new` で答えるので、返ってきた呼び出しをそのまま送れる。

### 行番号のずれは、srwr が吸収する

行番号で範囲を指定すると、編集を重ねるうちにずれる。Claude Code の Edit が `old_string` 方式を採っているのもこのため。srwr では、トークンに発行時点の `seq` を埋め込み、その後の編集履歴から自動で補正する。そのうえで内容のハッシュを照合し、一致しなければ編集しない（[token.md](token_ja.md)）。

### ツールを4つ（look・edit・replace・new）に絞る

カーソル移動系・取得系・検索系は持たない。検索や読み取りは、AI がもともと持つ Read・grep に任せる。srwr の責務は「実際にファイルが変わる瞬間と、その直前に見ている範囲を記録すること」だけ。可視化が単純になるだけでなく、似たツールが多いと LLM は選択を誤りやすいので、AI の利用精度にも効く。

### `why` を必須にする

`why` 付きの操作列でないと、人は AI の作業を理解しにくい。任意にすると、この価値が失われ、実際にも抜け落ちる。言語は、ユーザーとの会話と同じにする。人が読めない言語で書かれると、効果が出ない。

### 調べる過程も、同じテープに載せる

AI は、Bash・Read で調べ終えてから、直す箇所だけを `look` することが多く、調べる過程がテープの外に残る。そこで、hook で既存ツールの操作も同じテープに記録する。`srwr mcp` と `srwr hook` を1つのバイナリにまとめ、同じテープに書く。`why` のない（`null` の）コマとして表示される。

## テープと実ファイル

### 先に実ファイルを書き、そのあとテープに追記する

途中で落ちても、次に触れたとき実ファイルとテープの食い違いが `external` として見える。逆の順だと、テープにあるのに実ファイルにはない操作が残る。

### テープが内容を持つファイルだけを `external` の対象にする

一度も触れないファイルの変更は、基準がないので見えない。基準を持つ（セッション開始時に全ファイルのハッシュを持つ）と、テープが大きくなる。限界として受け入れている（[limitations.md](limitations_ja.md)）。

### どの種類のコマを送るかは、サーバーが決める

look・edit・external・failure の ON/OFF は、クライアントごとにもできる。しかしそれでは、番号の振り方、下のバーの位置、コマ送り、ライブの新着の数を、VSCode と Vim で2回作ることになり、食い違いうる。そこで、クライアントが欲しい種類（`kinds`）を伝え、サーバーがその種類だけを、番号を振り直して送る。クライアントは、渡されたものを描くだけでよい。切り替えは、開き直す。選んだ内容は、見た目の設定を持たない方針なので、保存しない。

### 失敗した呼び出しはテープに書き、頼まれたときだけ見せる

失敗した呼び出しは何も残らないので、AI が何度も繰り返すミス（絶対パス、`why` の抜け）は、AI に聞くまで分からなかった。テープに `failure` として持つ。ビューワーは、人が `failure` を ON にしたときだけ、赤いコマとして見せる（上の、種類の選び方）。絶対パス・作業場の外・記録しないファイルのときは、テープが共有されるので、実際のパスを書かない。

### 外部変更は、中身が見える形で挟む

ラベルだけでは、何が変わったか分からない。そのため、`external` と `final` は左右に並べた差分で見せる。ラベルは見出し（タブのタイトル）に出す。`why` の行と同じ形の行は、差分の画面では作れない。

テープは `external` を、ファイル全体でなく、変わった行（`hunks`）で持ち、直後に `snapshot` を続けない。測ったテープの 89% は全文で、その多くが同じ内容の2回分（`external` とその直後の `snapshot`）だった。全文は、ファイルごとに最初に触れたときの1回だけ持つ。変わった行は、同じテープが持つ内容に当てるので、テープは単独で再生できる。

### 表示サーバーは、テープに書かれたパスを信用しない

共有されたテープに、任意のファイルを読ませないため。最後の差分で今のファイルを読むとき、作業場の外を指すパス（`..`・絶対パス・外を指すシンボリックリンク）は読まず、「存在しない」として扱う。

## 表示の仕組み

### テープの形式は Go の中だけの約束にする

テープを読んでコマを組み立てる処理を、エディタごとに持つと、VSCode と Vim で食い違い、形式を変えるたびに全部を直すことになる。そこで、読む側を表示サーバー（Go）に1つに集め、エディタとの約束は [プロトコル](../reference/protocol_ja.md) だけにした。テープの形式の変更は、サーバーの中で吸収する。

### v1 までは、テープの形式の互換を約束しない

srwr はまだ実験の段階で、古いテープに頼る利用者はいない。古い形をすべて読めるように保つと、テープを軽く単純にすること（例：`external` と同じ全文を繰り返す `snapshot` をやめる）ができなくなる。そこで、v1 までは互換なしで形式を変えることがあり、テープは書いた版で読む。v1 からは、[tape.md](../reference/tape_ja.md) の約束どおり、フィールドは足せるが、既存の意味は変えない。

### 閉じたテープは gzip で圧縮する

テープの約9割は、各ファイルに最初に触れたときの全文（`snapshot`）。これは削れない（再生がテープだけで完結するため）。そこで、セッションが終わってからテープを小さくする。終わったセッションのテープは、次のセッションを始める呼び出しが、ロックの中で gzip で圧縮する（`<id>.tape.jsonl.gz`）。

- gzip は Go の標準ライブラリにある（依存を足さない）。`zcat` で読める。同じテープは必ず同じバイト列になるので、共有したテープは、もう一度圧縮しても変わらない
- 書き込み中のテープは、今までどおり JSONL のまま。追記も、ライブも、終わっていない最後の行の扱いも変わらない。テープを読むものは、どちらの形も開く
- 採らなかった案：変更されなかったファイルは、読んだ範囲だけ持つ（再生がテープだけで完結しなくなる）、イベントごとに圧縮する（目でも `grep` でも読めなくなる）
- 圧縮に失敗しても、ほかには何も起きない。圧縮していないテープが残り、今までどおり読まれる

### 通信は改行区切りの JSON

LSP 形式（ヘッダー付き）は、Vim が標準では扱えない。改行区切りなら、Vim 標準の `job` と `nl` モードのチャンネルでそのまま扱え、VSCode もライブラリなしで書ける。MCP と同じ形式なので、実装も共有できる。

### 1つのクライアントに1つのサーバー

共有のデーモンにはしない。共有の媒体は、テープそのもの。

### 外部依存を増やさない

Go は標準ライブラリだけ（MCP も表示サーバーも自前の JSON-RPC、ライブはポーリング）。VSCode 拡張はランタイム依存ゼロ。Vim は他のプラグインに頼らない。配布が単純になり（`go install` で入る、cgo なし）、依存の脆弱性・ライセンスを気にしなくてよい。

### VSCode 拡張に `srwr` のバイナリを同梱しない

拡張（`.vsix`）は単独で配り、`srwr` は別に入れる（`go install` か GitHub Releases。[cli.md](../reference/cli_ja.md)）。理由：AI に srwr を使わせる人は、どのみち `srwr` を入れる（`srwr mcp`・`srwr hook` がそのバイナリ）。Vim も同じバイナリを使うので、入れ方が1つにまとまる。拡張の中のバイナリは、AI が動かすバイナリと版がずれうる。OS と CPU ごとの `.vsix`（6個）も避けられる。代わりに、テープを見たいだけの人は2段の手順になる。見つからないときは、拡張が `srwr` の入れ方を案内する。

## UI の判断

画面の仕様は [vscode.md](../reference/vscode_ja.md)・[vim.md](../reference/vim_ja.md)。ここには、そう決めた理由を書く。

| 決めたこと | 理由 |
|---|---|
| **見るのはコマ送りだけ**。自動再生・速度・実時間のボタンはない | 見る人は、理由を読みながら1つずつ進める。動きは理解の助けにならず、確かめる部分も増える |
| **look は青、edit は橙**の2色。外部変更・録画後の丸だけ紫 | 少ない色で、種類を見分けられる |
| **`replace` のコマの理由は、先頭に1か所でなく、変わった行のまとまりごとの直前に出す** | 先頭に1か所だと、変更が下にあるとき帯が窓の外に出て、理由が読めない。まとまりは表示サーバーが渡す（`hunks`）ので、VSCode と Vim で同じになる。どのまとまりにも理由の全文を出し、変更のすぐ上で読める |
| **理由の行は、範囲の直前に、実際の行として差し込む**（濃い背景に白の太字）。範囲は同じ色の薄い色 | 理由とコードを、同じ場所で続けて読める。差し込むのは仮想ドキュメントなので、実ファイルには影響しない。代わりに行番号が合わなくなるので、実ファイルどおりの番号を自前で出す |
| **差分は左右に並べ、変わった行だけ塗る（前＝青、後＝橙）** | 何が変わったかが、中身で分かる。VSCode の標準の差分画面は色を替えられないので、左右2つのエディタに自前の色を付ける |
| **操作一覧は、1から順の平らな一覧** | 親子の字下げは見づらく、使いどころがない。番号は、下のバーの位置と同じ |
| **「戻る」「進む」と位置を、いつも出す**。行けない側は消さずに薄くする | 位置が動かないので、操作を覚えやすい |
| **ライブは録画と同じ画面**。追っている間は「● LIVE」、古いコマでは「LIVE に戻る（新着 N）」 | 別の画面を覚えなくてよい。古いコマを読んでいる最中に、画面を動かさない |
| **srwr に見た目の設定は持たない**（設定は `srwr` の場所だけ。Vim のハイライトグループは上書きできる） | 同じ見た目で共有でき、設定の組み合わせを確かめなくてよい |
| **実ファイルは開かない。ジャンプの表示もない** | テープだけで完結する。足りない情報は、コマの列に足す |
| **最後の差分を、差分のコマの1つとして残す** | 録画のあとのファイルの変更を、同じ見方で確かめられる |

## テストの考え方

- Go は表駆動。**わざとロジックを壊して、テストが落ちることを確かめる**。`t.TempDir()` の中で行う
- 表示サーバーは、全 fixture のテープで、コマの列が固定の正解データと一致することを確かめる
- 拡張のテストは、Go が書いた**実物のテープ**を fixture にする。手で書いたテープを使わない
- 見た目は自動のテストでは確かめにくい。画面の中身（文書、色の付け方、画面の数）はテストで、見た目そのものは目で確かめる
