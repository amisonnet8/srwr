# 範囲トークン

*[English](token.md) | **日本語***

**読者**：srwr を開発する人。この文書は単独で読むものではない。[mcp.md](../reference/mcp_ja.md)（`look` が返す `sel_…`）と [tape.md](../reference/tape_ja.md)（`from`・`selection`）から、詳細を知りたいときにリンクで来る。

**範囲トークン**は、`look` が返し、`edit` が受け取る文字列。「どのファイルの、どの行を、どの内容で見ていたか」を1つの文字列に封じ込め、AI はそのまま渡すだけで編集できる。

```
sel_0410R3GZE4KV11C6325D32S7
└┬┘ └───────┬────────┘
接頭辞   Crockford Base32（下記バイナリを符号化）
```

## 形式

中身のバイナリ（先頭から順に連結）：

| フィールド | サイズ | 内容 |
|---|---|---|
| version | 1バイト | 形式のバージョン（`1`） |
| seq | 可変長整数 | トークンを発行したイベント（`look` または `edit`）のテープ上の通し番号 |
| startLine | 可変長整数 | 開始行 |
| endLine | 可変長整数 | 終了行（空範囲なら `startLine - 1`） |
| fileHash | 4バイト | 対象ファイルの作業場相対パスの SHA-256 先頭4バイト |
| textHash | 4バイト | 範囲内テキストの SHA-256 先頭4バイト。テキストは範囲の行を `\n` でつないだもの（末尾の改行なし。テープの `oldText` と同じ形）。空範囲なら空文字列 |
| mac | 3バイト | **テープID**（テープのファイル名から `.tape.jsonl` を除いたもの。例：`20261001-1706-1795`）と上記すべてに対する HMAC-SHA256（鍵は `.srwr/key`）の先頭3バイト |

- 可変長整数は LEB128（Protocol Buffers の varint と同じ方式）
- 合計はおおむね15〜20バイトで、Base32 にすると**24〜32文字程度**になる
- テープID は mac の計算にだけ使い、トークンには含めない。そのため、別のテープ（別のセッション）で発行されたトークンは HMAC が一致せず、`invalid_selection` になる。短いID（4文字）だけでは別のテープと重なりうるので、日時を含むテープID 全体を使う

## 復号の許容

- 大文字小文字は区別しない
- Crockford Base32 の規約どおり、`O`→`0`、`I`・`L`→`1` と読み替える
- 区切りのハイフンは無視する

## 検証と行番号の補正

`edit` を受け取ったら、srwr は次の順で処理する（全体の順序は [mcp.md](../reference/mcp_ja.md)）。

1. **復号と HMAC 検証**：失敗したら `invalid_selection`
2. **ファイル特定**：テープの `snapshot` から作った「パス→fileHash」表で対象ファイルを引く
3. **行番号の補正**：トークンの `seq` より後に、同じファイルで行われた `edit` を順にたどる。トークンの範囲を `[a, b]`、その編集の（補正前の）範囲を `[s, e]`（空範囲は `e = s - 1`）とする
   - `e < a`：編集は範囲より上。`a`・`b` を「置き換え後の行数 − 置き換え前の行数」だけずらす
   - `s > b`：編集は範囲より下。何もしない
   - それ以外：編集が範囲と重なる（空範囲の挿入が範囲の内側に入る場合も含む）。補正できないので `selection_stale`
4. **内容の照合**：補正後の範囲の現在のテキストのハッシュが `textHash` と一致しなければ `selection_mismatch`
5. **実行**：置き換えてテープに追記し、新しいトークンを返す

ファイルへの編集はすべて srwr 自身が行っているので、「このトークンの発行後に何が起きたか」を srwr はすべて知っている。そのため AI は行番号の計算をしなくてよい。

`external`（srwr の外の変更）は、srwr が追える編集ではないので、補正は増えない。それより前に発行したトークンは、外部変更が範囲も範囲より上の行数も変えていなければ（たとえば範囲より下の変更なら）、そのまま使える。そうでなければ、内容の照合で `selection_mismatch` になる。外部変更の中身から行のずれを推定することはしない。

## 有効な範囲

トークンが有効なのは、発行したテープ（セッション）の中だけ。トークンの `seq` がテープ内の通し番号なので、別のテープでは同じ番号が別の操作を指すため。セッションが変わったら、AI は `look` し直す。

## 採用理由

| 選択 | 理由 |
|---|---|
| 文字列1つ | AI は JSON オブジェクトを書き写すより、文字列1つをそのまま渡す方が確実。テープ上の見た目もすっきりする |
| **Crockford Base32** | 大文字と数字だけで、`0/O`・`1/I/L` など紛らわしい文字を除いてある。大文字小文字を区別しないので、LLM の書き写しミスに強い（ULID と同じ方式）。base64 は大小文字混在でトークン数が増え、1文字ずれるミスも起きやすいので不採用 |
| **可変長整数** | 行番号や seq は小さい数が多いので、数バイトで済み、トークンが短くなる |
| **HMAC** | AI がトークンを解読して行番号を勝手に書き換えても検知できる。発行も検証も srwr 内で完結するので、JWT のような重い仕組みはいらない |
| `sel_` 接頭辞 | Stripe 式の ID 表記。何の文字列かが一目で分かり、別種の ID を取り違えたときにもすぐ気づける |
| 人間可読形式（`main.go:12-14@9f2c`）は不採用 | テープを読むには便利だが、AI が行番号部分を書き換えて使う誘惑が生まれ、「`look` の戻り値をそのまま渡す」狙いとずれる。人間向けには、テープにデコード済みの値を併記する |

HMAC の長さ（3バイト）は、書き写しミスの検出率と文字数のトレードオフ。見直すかは未定（[limitations.md](limitations_ja.md)）。
